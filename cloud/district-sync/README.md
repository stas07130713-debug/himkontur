# Резервная синхронизация карты ХИМКОНТУР

Cloudflare Worker является координатором записи, а D1 — резервной базой и журналом операций. Яндекс Cloud остаётся основной базой. При недоступности Яндекса Worker принимает изменения в D1; при восстановлении связи последовательно повторяет операции только при совпадении базовой версии.

## Безопасный порядок ввода

1. Создать базу D1 `himkontur-district-map` и подставить её `database_id` в `wrangler.jsonc`.
2. Применить миграцию `0001_initial.sql`.
3. Задать секреты Worker: `ADMIN_PASSWORD`, `SESSION_SECRET`, `PRIMARY_SYNC_TOKEN`.
4. Развернуть Worker, но оставить `coordinatorEnabled: false` в приложении.
5. Обновить функцию Яндекс до протокола v2 и задать тот же `PRIMARY_SYNC_TOKEN`.
6. Через `/v1/bootstrap` перенести текущую карту. Bootstrap разрешён только для пустой D1 и только если версия файла совпадает с живой версией Яндекс.
7. Сравнить revision, SHA-256 и количество объектов.
8. Включить `coordinatorEnabled` и адрес Worker в `public/data/map-sync.json`.

Если Яндекс недоступен, допускается одноразовая аварийная инициализация только утверждённой пользователем резервной копией. Запрос обязан содержать её SHA-256, `authoritativeRecovery: true`, уникальный `operationId` и последнюю подтверждённую ревизию Яндекса в `baseRevision`. Карта сохраняется в D1, а операция остаётся в очереди. После восстановления Яндекса она применяется только при точном совпадении базовой ревизии; любое расхождение переводит синхронизацию в безопасный конфликт без перезаписи данных.

Секреты не хранятся в репозитории. Запись напрямую в Яндекс после включения координатора запрещена на уровне клиента: это предотвращает расхождение двух облаков.

## Ограничение доступности

Если Cloudflare недоступен, чтение продолжает работать напрямую из Яндекса и локальных копий. Общие записи временно остаются в локальной очереди браузера. Это осознанное ограничение: разрешение независимых записей в оба облака создало бы split-brain и риск потери более новых данных.
